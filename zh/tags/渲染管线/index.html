渲染管线学习：从概念到 Unity URP 实践

本章路线 渲染流程看起来像一条直线，但完整的一帧通常由许多相互依赖的绘制步骤组成。理解时可以同时看两张图：第一张解释一个物体如何被光栅化；第二张解释阴影、深度、屏幕空间效果和后处理怎样组成一帧。 Q：渲染管线一帧里大致发生什么？ 先给出主干，再逐个解释数据如何流动。 下图描述常见的实时栅格化流程；不同图形 API、Unity 版本和渲染路径会改变具体实现与顺序。 flowchart LR 是观察空间到裁剪空间的投影矩阵，则： p_clip = P · V · M · p_local 这里的点积表示矩阵乘法；p_clip 是裁剪空间坐标。Vertex Shader 通常负责至少把位置变换到裁剪空间。投影除法和视口变换之后，位置才映射到屏幕坐标。uv（纹理坐标）、法线、颜色等数据则随顶点一起输出，并在三角形内部插值后交给 Fragment Shader。 片元不一定等于最终屏幕像素。 一个三角形可能在同一像素上产生覆盖片元；深度测试、裁剪、抗锯齿和多重采样会影响最终是否写入屏幕颜色。 两个常见着色阶段 Vertex Shader（顶点着色器）：每个顶点执行一次。常见工作是空间变换，也可以做简单顶点动画或位移。它输出顶点位置和要插值到片元阶段的数据。 Fragment Shader（片元着色器）：对覆盖区域产生的片元执行。常见工作是采样纹理、组合颜色、准备法线与材质属性，或计算最终颜色。 Shader 是管线中执行计算的程序；它不等于渲染管线本身。渲染管线还负责筛选对象、安排 Pass、建立缓冲区、选择状态并把阶段连接起来。 Shader 编程入门通常集中在 Vertex Shader 与 Fragment Shader，但它们只是整条渲染流程中由用户编写或配置的一部分。可见性筛选、Pass 调度、缓冲区生成、阴影数据、混合和后处理也都会影响最终画面。因此，先理解每一步的输入、输出和职责，再深入写 Shader，会更容易建立整体认识。 在前向渲染中，Lit Shader 往往会在片元阶段结合表面材质、灯光和阴影数据计算受光颜色；延迟渲染则可能先把表面信息写入 G-buffer，再由后续光照 Pass 计算光照。因而，“Fragment Shader 只准备基础颜色，之后总有一个独立默认光照步骤”不是通用规律。光源数据的组织、阴影可见性计算和表面着色可以由不同阶段提供，但最后会在光照结果中结合。 光照和阴影，可以说是渲染模块里最复杂的部分。它们涉及多个 Pass、不同数据来源和多种算法。 Q：现代渲染管线怎样组织光照与阴影的不同方案？ 现代实时渲染不是在一个固定主干末端依次添加“光照模块”和“阴影模块”。渲染器会根据画质、平台和场景，选择多种数据生成方式，再把它们的结果交给表面着色或后续合成。理解时可把“光照从哪里来”“表面是否被遮挡”“用什么算法求结果”分开看。 先区分光照相关概念 概念 含义 常见实现或输入 容易混淆的点 直接光照 光从光源到达表面，中间没有其他表面反弹 方向光、点光源、聚光灯；可配实时阴影 光照计算与阴影可见性有关，但阴影图的生成通常是单独的绘制工作 间接光照 光到达表面前至少经过一次其他表面反射 烘焙光照、探针、实时 GI、SSGI、光线追踪 GI 全局光照（GI）通常指模拟间接光照的方法，不等于 AO，也不只是环境光颜色 环境光照 对天空、环境和大量远处表面贡献的近似表示 环境颜色、球谐光照、Light Probe、环境立方体贴图 它是光照贡献或其近似输入；采用某种环境光并不表示完整求解了光线反弹 环境光遮蔽（AO） 估算周围几何对半球方向环境光的遮挡程度 烘焙 AO、SSAO、GTAO、光线追踪 AO AO 是局部可见性近似，不会生成直接光，也不等于完整 GI 或普通投影阴影 阴影 判断光源到受光表面的路径是否被物体遮住 Shadow Map、Shadow Mask、屏幕空间估算、光线追踪 阴影是光照可见性的一部分；它自身通常不负责产生受光颜色 反射 表面把环境或其他物体的光反射到观察方向 Reflection Probe、SSR、平面反射、光线追踪反射 反射属于镜面方向的环境贡献，与漫反射 GI 相关但不是同一项 “环境光照”和“全局光照”不是同义词。环境光照可以用简单颜色或环境探针近似；全局光照方法则尝试表示表面之间的光传递。环境项可以成为间接光照的一个输入，但环境颜色本身并没有逐次追踪场景中的反弹过程。 阴影与间接光照有哪些路线？ 路线 主要数据 优点 代价与限制 Shadow Map 实时阴影 从光源视角绘制的深度图 适合动态物体；成熟、适用面广 计算便宜，适合环境镜面光照近似 位置、遮挡和动态几何精度有限 SSGI 屏幕空间深度、法线和颜色 可补充相机可见区域的漫反射反弹 只能利用屏幕上已有信息，容易缺失离屏间接光 光线追踪 GI 场景加速结构和多方向的光线查询 能处理较复杂的遮挡、反弹与颜色溢出 计算量高，常需降采样、限制反弹次数和时域降噪 发射光线，再把估算结果降噪后合入。光线追踪 API 通常有独立的射线生成、命中与未命中等 Shader 类型；它们不等同于传统 Vertex/Fragment Shader 的后续 Pass。Microsoft DXR 着色阶段；DXR 光线生成 Shader “屏幕空间光照”是对一组读取当前相机缓冲数据、在屏幕坐标中估算光照相关贡献的方便统称，不是一个具有唯一算法定义的单独技术。它们通常使用深度、法线，有时也使用颜色、材质粗糙度、运动向量和灯光信息。由于输入来自当前画面，效果的成本通常与屏幕像素和采样数量密切相关。 常见技术各自估算什么？ 技术 主要输入 估算贡献 典型缺失或伪影 SSAO / GTAO 深度与法线 近处几何对环境光的局部遮挡 不计算完整反弹光；半径过大时会产生不真实的整体变暗 屏幕空间接触阴影 深度、法线、光源方向 已有阴影图较难表现的细小接触遮挡 受屏幕可见性和深度精度限制，不是完整的光源阴影 SSGI 深度、法线、场景颜色 屏幕可见表面的近似漫反射反弹与颜色溢出 离屏反弹光、被遮挡物体和复杂多次反弹信息缺失 SSR 深度、法线、粗糙度、场景颜色 沿反射方向在屏幕深度数据中寻找交点并采样颜色 画面外、被遮挡或未写入颜色缓冲的物体无法正常反射 SSAO 对“周围几何挡住环境方向”的估算可以提高接触与角落的层次，但这只是局部遮蔽近似。SSGI 试图从已有屏幕颜色估算一次间接漫反射；SSR 估算镜面方向的反射颜色。它们的输入、输出和物理意义不同，不宜统称为同一种 AO 或 GI。HDRP 13.1.9 的 SSGI 文档明确说明它使用屏幕深度和颜色缓冲估算漫反射反弹；这与 SSAO 和 SSR 的目标不同。HDRP 13.1.9 Screen Space Global Illumination 屏幕空间效果在管线中读取什么、写出什么？ flowchart TB A[场景几何 / 材质 / 灯光] --> B[深度、法线与材质数据生成] B --> AO[SSAO / GTAO] B --> SH[屏幕空间阴影] A --> SH A --> C[前向或延迟 Lit 光照] AO M --> T[透明绘制 / 后处理 / 显示] 上图是数据依赖图，不承诺所有技术都会在主颜色绘制之后执行。比如 SSAO 可以被光照着色读取，也可以在已着色画面上合成；SSR 通常要等场景颜色可用后才能采样。实际顺序由渲染路径、Renderer Feature、相机缓冲需求和效果实现决定。 为什么它们会丢信息？ 屏幕缓冲只保存当前相机已经绘制出来的数据。被墙挡住的物体、相机视野外的物体、没有进入深度或颜色缓冲的透明表面，都不一定能成为屏幕空间算法的查询对象。因此 SSR 可能在屏幕边缘断裂或找不到反射；SSGI 也可能漏掉画面外的反弹光。屏幕空间反射只能反映当前屏幕可见的数据，这也是实际管线常把它和 Reflection Probe、天空环境或光线追踪反射组合的原因。Unreal Engine：反射与屏幕空间反射限制 时域累积可以利用前几帧的信息降低噪点，但相机或物体运动时可能出现拖影、闪烁或历史信息失配；降噪、抖动采样和运动向量能改善观感，也会增加实现与调试复杂度。增加分辨率、屏幕覆盖面积或采样数量也会提升计算成本。 选择屏幕空间效果时，可以依次确认：需要估算哪种贡献？需要深度、法线还是颜色？目标对象是否会进入这些缓冲？缺失画面外信息时用什么回退？效果在哪个管线时机合成？ 这些问题通常比从一个算法名称开始更容易定位实现方式。 Q：Lit、Unlit 与 Forward Rendering 是什么？ 先区分两个维度：Lit / Unlit 描述材质着色是否采用常规表面光照逻辑；Forward / Deferred 描述渲染器如何组织几何绘制与光照计算。 Lit 不是 Forward 的同义词，Unlit 也不代表物体不会参与任何深度、阴影或屏幕空间处理。 概念 它回答的问题 典型行为 Lit Shader 表面怎样响应光？ 使用表面颜色、法线、粗糙度等材质数据，结合可用光照计算颜色；URP Lit 通常支持直接光、阴影、间接光与镜面环境贡献，具体受材质、Pass 和管线设置影响 Unlit Shader 是否运行常规表面光照模型？ 默认直接输出材质或节点计算出的颜色，不因场景灯光方向而改变；仍可能参加深度绘制，也可能由后续效果或专门实现影响 Forward Rendering 怎样绘制并计算可见表面的光照？ 绘制物体表面时就着色；Shader 在该次绘制中读取适用于物体/片元的光源与其他光照数据并计算颜色 Deferred Rendering 怎样把表面信息和光照计算分开？ 先把可见表面属性写入 G-buffer，再由后续光照 Pass 读取这些属性并计算光照 Forward Rendering：绘制表面时计算光照 在前向渲染中，渲染器选择当前相机可见的物体并安排绘制。物体的 Forward Pass 运行 Vertex Shader、光栅化和 Fragment Shader；Lit Fragment Shader 根据表面数据以及 URP 提供的灯光、阴影和环境数据计算受光颜色。简单理解就是“表面被绘制时完成着色”，而不是先为全屏每个像素保存一套表面属性、再统一算光。 这不表示每个 Fragment Shader 都会自动获得完整 Lit 功能。URP 会剔除、整理当前相机和物体可用的光源，并提供 Shader Library 等接口；Lit Shader 或自定义 Shader 仍需通过相应代码消费这些数据。传统 Forward 路径还会受到每物体附加光源数量等设置约束。在支持 Forward+ 的 URP 版本中，它使用分块/聚类的光源列表改善大量光源场景下的光源访问方式，但仍属于前向着色思路。 flowchart LR A[相机可见性筛选] --> B[URP 整理当前绘制可用的光源与阴影数据] B --> D[Lit Forward Pass] C[网格顶点] --> E[Vertex Shader] E --> F[光栅化与属性插值] F --> G[Fragment Shader：表面数据 又替我们处理了什么？ 在常见的前向渲染中，Lit Shader 通常在 Fragment Shader（片元着色器）阶段对表面应用光照模型。完整画面还可能组合实时灯光、烘焙间接光、环境光、反射与屏幕空间效果；它们由不同的数据准备步骤或 Pass 提供，不一定全部在同一个 Shader、同一个阶段完成。 设 n 为单位表面法线，l 为指向光源的单位方向，ρ 为表面对漫反射光的反射比例（RGB 颜色），I_L 为光源颜色与强度的乘积。最简单的 Lambert 漫反射可写成： C_diff = ρ · I_L · max(0, n · l) n · l 是法线与光方向的点积；表面背向光源时它小于零，因此用 max(0, …) 将贡献设为零。这个公式只说明一个方向光对漫反射的简化贡献，不是 Unity Lit 的完整 PBR 公式。 Unity / URP 如何准备光照，Shader
